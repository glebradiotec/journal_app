# journal_app

Flask-приложение для редакции журналов издательства «Радиотехника». Два независимых модуля
живут в одном приложении, в одной БД, но **никак не пересекаются**:

1. **Учёт статей** (`models.py`, `routes_admin.py`, `routes_author.py`, `routes_public.py`) —
   повседневный рабочий инструмент сотрудницы: заводит статьи, отслеживает оплату/рецензию/
   редактуру. Таблицы `Article`, `Issue`, `ArticleAuthor`, `Journal`, `User`, ...
2. **«Публикация на сайте»** (`models_publish.py`, `routes_publish.py`,
   `article_template_parser.py`, `site_db.py`, `export_crossref.py`, `export_elibrary.py`,
   `templates/publish/*`) — отдельный процесс: разбор .doc/.docx/.rtf статьи → запись напрямую
   в БД боевого сайта radiotec.ru (`radiotec_main4`, MySQL) → генерация XML для CrossRef (DOI) и
   eLibrary. Свои таблицы `PubIssue`/`PubArticle`/`PubAuthor`/`PubSection`.

**Жёсткое правило от пользователя: эти два модуля не должны смешиваться.** Не переиспользовать
`Article`/`Issue` для публикации на сайт, не трогать рабочий процесс сотрудницы при доработке
модуля публикации, и наоборот. Общее — только стиль интерфейса (`templates/base.html`, `adm-*`
CSS-классы, тема) и логин/сессия.

## Известные грабли

- Flask-SQLAlchemy резолвит `sqlite:///journal.db` относительно `instance/`, не cwd. Любой
  самостоятельный скрипт с БД должен явно собирать путь через `os.path.isabs(...)` +
  `instance/`, иначе создаст пустую БД не в том месте.
- `app.jinja_env.auto_reload = False` — правки шаблонов не подхватываются без рестарта воркеров.
- `.doc` (старый бинарный Word) в учёте статей парсится через `catdoc -a -d utf-8 -w` (основной способ,
  корректно определяет кириллицу), `antiword` — только запасной вариант (даёт литеральные `?`
  на части файлов). Модуль публикации читает `.doc` иначе — см. «Чтение .doc» ниже.
- `.env` на проде должен читаться пользователем службы: `journal.service` работает от `www-data`, не от root. Права 600 на
  `.env` (root) = воркеры не стартуют, 502 (случилось 2026-10-12 после `tools/site_connect.py setup`). Правильно: root:www-data, 640.
- SSH/SCP на прод нестабилен на длинных/больших передачах — чанковать переносы, длинные операции
  запускать через `nohup ... & disown` и поллить короткими подключениями.
- Windows Git Bash: путь `C:/...` в `tar` парсится как `host:path` — нужен `--force-local`.

## Метафора (ИС РЦНИ)

- `metafora_api.py` — клиент API v2 (ключ только из `METAFORA_API_KEY` в `.env`), `export_metafora.py` — Journal XML,
  `export_refs.py` — связывание русского и английского списков литературы. Шаги отправки — на странице выпуска (раздел «Публикация»).
- `tools/metafora_issue.py` — выпуск из папки с `.doc` и PDF целиком, без интерфейса: `build` (XML из папки),
  `check` (сверка XML с напечатанными PDF), `send [--replace]` (XML + PDF статей, без подписи), `verify` (сверка
  того, что лежит в Метафоре, с PDF). Состояние отправки — рядом с XML, `*.xml.state.json`.
- PDF — независимая проверка разбора. Отправлять выпуск без `check`/`verify` нельзя: ошибки разбора (потерянный
  автор, пустая ссылка) по одному XML не видны.
- Выпуск мог попасть в Метафору не из раздела (CLI, вручную): `GET /publications/doi/<doi>` отдаёт `file_uid`, `has_pdf`,
  `signed_at`. Раздел сам подхватывает такой выпуск (`_mf_link`, `metafora/link`): при открытии страницы неотправленного
  выпуска (проба одного запроса), при «Отправить» (вместо повторной загрузки) и кнопкой «Сверить с Метафорой» на начальной.
  Частично найденный или разложенный по разным файлам выпуск не подхватывается — только отказ с пояснением.
- Подписание публикаций в Метафоре блокирует правки — только по явной просьбе пользователя.

## Раздел «Публикация выпусков» (интерфейс)

- Вход — кнопка на главной; раздел открыт всем сотрудникам (`publish_required` в `routes_publish_hub.py`), внешним
  авторам закрыт. Запись в БД сайта (`.../confirm`) — только администраторам.
- Навигация раздела единая: путь («Публикация › Журнал › Выпуск › страница») рисуется ВНУТРИ общей плашки сверху (`header.html`, слот
  `#gh-crumbs`), а не отдельной строкой. Страница только описывает его скрытым блоком `[data-gh-crumbs]` (`publish/_topbar.html`, внутри
  `.adm-main` — его заменяет SPA-переход), `base.html` (`__syncCrumbs`) копирует блок в плашку при загрузке и после каждого перехода. Текущая страница —
  цветная капсула `gh-crumb-current`; на телефоне видна только она. Заголовок страницы — блок `.pub-pagehead` (слева заголовок и строка
  описания, справа ОДНО главное действие `pub-btn-primary`, прочие тихие `pub-btn-ghost`); дублей кнопок нет.
  Страницы учёта статей (журналы, выпуск, статья, автор) своих шаблонов не меняли: у них есть `<ul class="breadcrumbs">`, и тот же `__syncCrumbs`
  переносит её звенья (кроме первого «Главная») в плашку, а саму строку прячет (`gh-crumbs-src`). Админские страницы плашки не имеют (у них боковая панель) —
  крошки там не нужны.
- Страницы раздела — обычные страницы сайта с общей шапкой (`body.pub-body`), без меню админки. Классы
  `adm-layout`/`adm-main` в шаблонах оставлены намеренно: по ним `base.html` при переходах внутри раздела заменяет
  только содержимое. Ссылка на `publish.css` идёт с `?v=` по времени изменения файла.
- Загрузка выпуска целиком: на начальной странице раздела только кнопка «Загрузить выпуск» (рамка с инструкцией там была
  перегрузом и убрана); сама загрузка — `/admin/publish/import` (`_import_widget.html` + скрипт
  `_import_widget_script.html`) → `publish_import.py`. Карточки журналов на начальной одной высоты: 4 последних выпуска, внизу «Все выпуски» и ISSN. Скрипт подключается на
  верхнем уровне страницы, не внутри `.adm-main`: иначе при переходах внутри раздела `base.html` его не выполнит. Файлы шлются по одному; реквизиты выпуска
  читаются из DOI статей. PDF статей лежат в `uploads/publish_issue_pdfs/<id>/` и подбираются по DOI на первой странице.
- Если выпуск из загрузки уже есть в разделе, предлагается «Открыть существующий» или «Заменить новой загрузкой»
  (`create_issue(..., replace=True)`: старый черновик удаляется с PDF и рукописями в одной транзакции с созданием нового; сбой —
  старый остаётся). Заменить нельзя, если выпуск записан на сайт или отправлен в Метафору (`replace_blocker`).
- Страница выпуска: сверка черновика с PDF (`metafora_check.py`) и шаги Метафоры — `metafora/start` (XML; отказ, если
  статьи выпуска уже есть в Метафоре), `poll`, `pdf`, `verify`, `sign-one` (только после сверки без ошибок).
- Действия выполняются на странице выпуска, без переходов: eLibrary и Метафора — `export/<kind>` (XML собирается в момент
  скачивания из текущих данных, поэтому не бывает «устаревшей выгрузки»); CrossRef собирается при записи на сайт и
  скачивается тем же адресом; запись на сайт — панель проверки (`site-check`, только чтение) → форма `confirm`,
  возвращающая на страницу выпуска. Отдельной страницы предпросмотра нет (старый адрес перенаправляет).
- Запись на сайт (боевая БД radiotec.ru, MySQL/MyISAM — транзакций нет): при записи запоминается, что она создала
  (`instance/publish_exports/<id>_site_push.json`: выпуск, разделы, статьи); при любом сбое созданное убирается само
  (`site_db.delete_created`), а «Откатить запись на сайт» (только админ) удаляет записанные статьи и созданные пустые
  раздел/выпуск (`site_db.rollback_push`; статья удаляется, только если по её art_id лежит тот же DOI). Подключение к
  боевой базе включается скриптом `tools/site_connect.py setup` (логин и пароль вводятся в терминале, не в чат);
  `ping` — проверка только на чтение. Пока `SITE_DATABASE_URL` не задан, запись идёт в локальную тестовую SQLite.
- Поля статьи для сайта собирает одна функция `routes_publish._site_fields` — и проверка перед записью (`_site_precheck`),
  и сама запись; пределы колонок берутся из БД сайта (`site_db.column_limits`) и проверяются ДЛЯ ВСЕХ полей (в колонке
  `citata`/`citata_eng` — 400 знаков, `art_name_eng` — 300). Строка «Для цитирования» (`citata`), не влезающая в 400, не
  отклоняется, а получает первых трёх авторов + «и др.» / «et al.» (`publish_format_html.format_citation_fit`; затем одного);
  поле `authors` на сайте при этом остаётся полным. Сокращение объявляется в проверке перед записью.
- Блок авторов на сайте: номер сноски отделён пробелом от организации и e-mail («1,2 МГТУ…», «1 a@b.ru, 2 c@d.ru» — как в
  статьях, внесённых вручную; без пробела «1,2МГТУ» слипалось). Уже записанное исправляет `tools/site_fix_authors.py`
  (без `--apply` только показывает; строки, правленные вручную после записи, пропускает).
- Раздел НЕ про одну Метафору: у выпуска четыре равноправных назначения — сайт radiotec.ru, eLibrary, CrossRef,
  Метафора. В интерфейсе (плитки состояния, карточки «Сайт, eLibrary, CrossRef» и «Метафора», тексты главной раздела)
  Метафора не должна выделяться; подробные шаги с подписью есть только у неё, потому что только у неё они бывают.
- Локальная проверка интерфейса на Mac: `python3 dev_mac_server.py` (порт 5055, своя БД, имитация Метафоры в памяти).

## Слежение за FTP (новые номера журналов)

- `tools/ftp_watch.py`: `setup` (адрес/логин/пароль вводятся в терминале, пишутся в `.env` как `FTP_HOST/PORT/USER/PASSWORD/TLS/ROOT/ENCODING`,
  пароль в двойных кавычках), `ls` (дерево папок, только чтение), `check [--dry]` (обход папки → сравнение со снимком
  `instance/ftp_snapshot.json` → сводка в Telegram токеном и чатом приложения `TELEGRAM_BOT_TOKEN/CHAT_ID`), `install` (systemd-таймер
  `ftp-watch.timer`: 10:00 и 14:00 `Europe/Moscow` — сервер живёт по Амстердаму, поэтому пояс указан в самом расписании).
- Только чтение: утилита ничего не загружает и не удаляет на FTP. Сначала пробует FTPS, при отказе — обычный FTP (в `setup` об этом
  предупреждает). Листинг — MLSD, а если сервер её не знает, то LIST (unix- и DOS-формат).
- SFTP (`FTP_PROTO=sftp`, порт 22; настоящий сервер — `85.30.219.155`, OpenSSH 8.2; первый адрес `109.197.26.84` был указан ошибочно): нужен `paramiko`
  (`venv/bin/pip install paramiko` на сервере, в репозитории requirements.txt нет). При `setup` запоминается отпечаток ключа сервера (`FTP_HOSTKEY`); при каждом
  подключении ключ проверяется ДО отправки пароля (`HostKeyChanged` — отказ). Папка `FTP_ROOT` для SFTP — относительно домашней (`.` или «журналы текущие»).
- Снимок запоминается только после того, как Telegram принял сводку: при сбое новое не «теряется», а попадает в следующую.
- Структура на сервере (SFTP `85.30.219.155`, пользователь `gleb`; похоже на NAS Synology): «Журналы текущие» → журнал → ГОД → папка номера
  (`Emw_04-2026`, `02-03_2008`) → макет/doc/pdf. Рядом «Radiotec», «АРХИВ», «Книги текущие», «chat», «home» — не отслеживаются. При проверке
  (`default_prune`) смотрятся только текущий и прошлый год (`FTP_YEARS_BACK`, `all` — всё; архив с 2008 года — 2000+ папок), в журнале — только
  папки-годы (не «font», «TEMP»), служебное игнорируется («#recycle», «._DAV», .DS_Store, `~$…`, папки-журналы из одних цифр вроде «1111111»).
  Папка без прав чтения пропускается и называется в сводке. Выпуск в сводке — «2026 №10» (`issue_title`: номер из названия папки), последний по
  журналу — по (год, номер). Сверка с разделом «Публикация» (есть ли такой выпуск) пока не сделана — названия папок журналов нужно сопоставить с `PubIssue`.

## Чтение .doc

- Только для модуля публикации (`pdf_parser.extract_text_any`); учёт статей (`parse_article_docx`) читает `.doc`
  по-старому, и менять это нельзя — см. правило про два модуля.
- Основной способ — `doc_text.py` (свой разбор формата, без внешних программ): отличает мягкий перенос строки от
  конца абзаца (строка-продолжение помечается U+2028), убирает коды полей Word, расшифровывает знаки из
  «Вставка → Символ». catdoc / textutil (macOS) / antiword — запасные.
- По меткам мягких переносов `article_template_parser` делит список литературы точно (абзац = ссылка). Без меток
  (текст из catdoc) — по виду строки плюс сверка русского списка с английским; этот режим ошибается примерно в
  3 статьях из 150.
- `.docx` читается тем же способом (`doc_text.extract_docx_text`, без python-docx): python-docx теряет неразрывный дефис
  Word — «1–4» у номера организации читалось как «14», и организации не привязывались к авторам.
- Разделы выпуска берутся из титульного PDF («Содержание»): заголовки заглавными буквами, у каждой статьи в конце
  строкой номер её первой страницы (`pdf_parser._toc_page_sections`). При загрузке выпуска разделы создаются, а статьи
  по первой странице получают свой раздел. Журналы без заглавных рубрик (Нелинейный мир, Успехи) разделов не имеют.
- Заголовки шаблона сравниваются без пробелов («Дляцитирования» слитно бывает в самих рукописях и в печатном PDF —
  `_canon_heading`, в `metafora_check` то же). Если у автора «нет английской организации», а в документе английских
  организаций меньше, чем номеров у авторов — ошибка в самой рукописи (так в РТ 2026 №8, Королёв), парсер её не чинит.
- Ключевые слова режутся по «,» и «;» вне скобок и кавычек (`split_keywords`, он же разбирает строку из БД —
  `PubArticle.keywords_*_list`; запятая в «(EGP, IGP)» — часть слова, а в английской строке «;» бывает вместо «,»).
  `equalize_keywords` (при разборе и при каждой выгрузке XML — `PubArticle.keywords_pair`, поэтому работает и для черновиков,
  сохранённых раньше; на сайт слова уходят как есть): в eLibrary слов должно быть поровну, поэтому аббревиатуры, образованные от предыдущего слова
  («machine learning, ML»), вклеиваются в него — только если числа после этого сошлись. Остальные расхождения (разные
  слова у автора) показываются на странице выпуска замечанием, а XML для eLibrary при них не собирается (Метафоре поровну
  не нужно). Из 162 статей на диске расходятся ещё 16.
- Форма статьи: ключевые слова правятся таблицей пар «русское ↔ английское» (`#kwBox` в `article_form.html`, JS inline):
  счётчик «поровну», пометка у слова: «в тексте ×N» / «частично» / «нет в тексте» (заглавие+аннотация, по основам слов),
  ✕ убирает слово и поднимает следующие, ↑↓ меняют местами, + вставляет пропуск НАД словом (так чинится слово,
  потерянное автором в середине списка: пары ниже встают на место).
  «✓» у номера строки — пара совпадает по написанию (транслитерация + пары букв: ГНСС↔GNSS). Автоматически искать, ГДЕ потерялось
  слово, пробовали и отказались: по буквам верное место называется первым в 82% искусственных пропусков, но на настоящих
  расхождениях (Успехи №9) промахивается — для смысловой сверки нужен перевод; поэтому таблица только показывает, не гадает. Таблица строится поверх двух скрытых полей `keywords_ru`/`keywords_en` — они
  и сохраняются (серверная часть не менялась); автозаполнение по файлу обновляет таблицу через `window.kwReload()`.
- Что умеет парсер сверх шаблона (всё найдено на «Биомедицинской радиоэлектронике» 2026): иностранные авторы полным именем
  («Али Султан Маея1», в том числе внутри списка с инициалами; английская фамилия выбирается по транслитерации русской, потому что
  порядок слов бывает другим: «Ibrahim Anagheen» при русском «Анагим Ибрахим»); номер организации ДО имён («1,2 N.O. Sitkov, …»);
  пропущенная запятая между авторами; заголовки с латинской буквой-двойником («Cписок») и опечаткой в одну букву («Ключевые слов»);
  том с латинской «T.»; хвост длинного URL после жёсткого переноса («…Resp» + «_Rate»). Ошибки самих рукописей парсер не чинит и не угадывает:
  автор без организации (Нагорнов, Смирнов), нет английской ссылки при русской (Клыпин–Титов) — такое правят вручную в форме статьи.
- Форма статьи: список источников — таблица пар «русская ↔ английская ссылка» (`#refBox`, JS inline, поверх скрытых `references_text`/
  `references_en_text`). Номера сбиваются, когда ссылка разорвалась (хвост адреса отдельной строкой) или пропала в одном языке. «Отпечаток»
  ссылки, одинаковый в обоих языках, — числа (год, том, страницы, DOI) и латинские слова: по нему находится ЛИШНЯЯ строка более длинного списка
  (точность 99,9% на 6848 искусственных пропусков и 3424 разрезанных ссылках из 242 статей) и предлагаются действия: «Склеить с предыдущей»
  (хвост начинается с «_», строчной буквы и т.п.), «Вставить пропуск в другом языке», «Убрать строку». У номера «✓» — годы/страницы пары совпали
  (98,7% правильных пар), «?» — не совпали (ложных 0%, на сдвинутых парах 96%).
- Парсер сам сверяет себя и пишет предупреждения: число авторов против «Для цитирования», русские авторы против
  английских, длина русского списка литературы против английского. Предупреждение почти всегда значит ошибку разбора
  или опечатку в статье — не игнорировать.
